# Проект: Helpdesk, выпуск v1.0.0

Этот документ подготовлен для ЭК1 курса «Разработка безопасного ПО». Разделы 1–5 описывают выбранный объект, методологию, фактическое состояние, целевой процесс и план апробации. Результаты исходных проверок подтверждают работоспособность каркаса; итоговое решение о выпуске будет принято на ЭК2.

## 1. Паспорт проекта

**Участник:** один студент — владелец будущего GitHub-репозитория. ФИО и учебный адрес добавляются перед публикацией вместе с адресом репозитория; они не были предоставлены при подготовке этого комплекта.

**Название проекта и команды:** Helpdesk.

**Формат:** индивидуальное выполнение по сообщению автора о допустимости такого формата. Опубликованные общие инструкции рассчитаны на пару. Работа второго участника и взаимная проверка в этом комплекте не заявляются.

**Продукт:** серверный сервис для регистрации и решения обращений пользователей.

**Планируемый выпуск:** `v1.0.0` для локальной учебной среды; код каркаса имеет версию `0.1.0`.

**Исходное состояние (baseline):** commit `f58554c3ef048ac3652e2c265c48a76c30e78e91`, tag `baseline-ek1`; каркас до дальнейших улучшений для ЭК2. Проверка: `git rev-parse baseline-ek1^{commit}`.

**Срез ЭК1:** tag `ek1`, создаваемый после финального заполнения реквизитов.

**Репозиторий:** локальный каталог `helpdesk`; удалённый репозиторий пока не создан. Публикация, доступ преподавателю и регистрация ссылки — оставшиеся организационные действия, а не уже выполненные шаги.

### Контекст и пользователи

Продукт рассматривается как небольшой внутренний сервис поддержки учебной организации. Этот контекст условный: реального заказчика, производственной среды и данных сотрудников нет. Разработку, проверку и подготовку выпуска выполняет один студент. Он же принимает решение о пригодности версии для заявленной учебной среды, учитывая ограничения самостоятельной проверки.

Пользователь сообщает о проблеме, просматривает свои обращения и ответы. Специалист выбирает обращение из очереди, принимает его в работу, обсуждает проблему и записывает решение. Внутренние заметки нужны для служебной диагностики и не предназначены пользователю. При повторном открытии обращение возвращается в очередь, а следующий специалист получает всю историю.

Для пользователя важны конфиденциальность переписки и достоверный статус решения. Для специалиста — корректное назначение и возможность сохранить внутренние сведения. Для сопровождающего — повторяемая сборка и понятное восстановление среды. Регистрация, самостоятельная смена пароля и управление персоналом пока не входят в продукт: четыре искусственные учётные записи создаются в отдельном демонстрационном режиме.

### Границы

В проект входят REST API, сессии и проверка полномочий, PostgreSQL, миграции Flyway, зависимости Gradle, Dockerfile, Compose, тесты, инструкция запуска и конфигурация GitHub Actions. Один выпуск включает согласованное состояние исходного кода, схемы БД, образа приложения и документации.

За границами остаются браузерный интерфейс, почта, загрузка файлов, корпоративный вход, несколько организаций, платёжные операции, публичный сервер и инфраструктура GitHub как сервиса. Настройки собственного репозитория и workflow остаются в области проектирования процесса. Реальные персональные данные и производственные секреты не используются.

Ограничение оправдано: текстовые обращения уже дают законченный процесс и существенные задачи защиты. Вложения и внешние интеграции увеличили бы объём анализа без необходимости для выбранного выпуска. Подробный [контракт API](docs/api.md) задаёт действия ролей и переходы статусов.

### Компоненты, взаимодействия и границы доверия

```mermaid
flowchart LR
    U[Пользователь / API-клиент] -->|HTTP, сессия, CSRF| A[Helpdesk: Kotlin + Spring Boot]
    S[Специалист / API-клиент] -->|HTTP, сессия, CSRF| A
    A -->|JDBC: параметры запросов| D[(PostgreSQL)]
    D --> V[Именованный Docker-том]
    G[Исходный код и Gradle] --> B[Сборка и тесты]
    R[Репозитории зависимостей и образов] --> B
    B --> I[Образ приложения]
    I --> A
```

| Граница | Что проходит | Почему существенна |
| --- | --- | --- |
| Клиент → API | Пароль, cookie, ID обращения, текст и команды | Клиент полностью недоверенный; ID и заявленная роль не являются разрешением |
| Пользователь → данные другого пользователя | Попытка доступа через ID и списки | Должна сохраняться изоляция обращений при каждом чтении и изменении |
| Пользователь → полномочия специалиста | Назначение, решение, внутренние заметки | Требуются проверки операции, объекта и доступных полей |
| API → PostgreSQL | Параметризованные запросы и миграции | Нельзя превращать входной текст в SQL; полномочия соединения ограничивают последствия ошибки |
| Код и внешние компоненты → образ | Зависимости, плагины, базовые образы | Изменение состава сборки влияет на доверие к проверенному выпуску |
| Локальная среда → GitHub | Код, конфигурация, результаты проверок | `.env` и другие секреты не должны попасть в историю или артефакты CI |

Loopback ограничивает доступ к API с сети, но не делает клиент доверенным. Пользователь компьютера с доступом к Docker считается администратором среды; защита от такого администратора не обещается.

### Доступные материалы и ограничения

Доступны весь исходный код, миграции, конфигурация, прямые и транзитивные зависимости, автоматические тесты и Docker-среда. Исходное состояние фиксируется локально в Git. Приложение можно изменить и повторить проверку самостоятельно; лицензии внешних сервисов и закрытые рабочие материалы не нужны.

Конфигурация CI подготовлена, но удалённый запуск до публикации не выполнен. Доступ преподавателю и адрес репозитория пока не подтверждены. Результаты текущей проверки собраны в [evidence/verification.md](evidence/verification.md); они не распространяются на неизвестную производственную среду. Пример исходного Kotlin/Gradle-проекта автора использован только как ориентир сборки; его данные и конфигурационные секреты не переносились.

Выполнимость обеспечивается небольшим числом сущностей, единой БД, локальным запуском и воспроизводимыми сценариями. Для ЭК2 можно улучшить ограничение попыток входа или разделение полномочий БД и проверить результат до и после. Окончательное улучшение выбирается после апробации, а не под заранее придуманный дефект.

## 2. Методологическая основа

### Требования к основе и сравнение кандидатов

Нужна рамка, охватывающая путь от требований до выпуска и обработки проблем, допускающая одного исполнителя, не зависящая от языка и не требующая недоступной производственной инфраструктуры. Положения должны превращаться в небольшие проверяемые действия. Источники и точные редакции перечислены в [docs/sources.md](docs/sources.md).

| Кандидат | Назначение и применимость | Адаптация и ограничения | Доступ и решение |
| --- | --- | --- | --- |
| **NIST SP 800-218, SSDF 1.1** | Практики безопасной разработки на всём жизненном цикле; подходят небольшому API | Ответственность совмещается, выбираются семь задач; нет готового локального процесса и детальных правил доступа | Открыт полный официальный текст; **основная рамка** |
| **OWASP SAMM 2** | Оценка зрелости и программа развития практик | Для нового продукта почти нет истории, чтобы обосновать уровни; полноценная оценка организации несоразмерна | Открытая модель; сравнили, **не включаем** в профиль |
| **ГОСТ Р 56939-2024** | Требования к процессам разработки безопасного ПО; применим при соответствующем контексте | Потребуется отбор процессов и упрощение ролей; обязательное применение заказчиком для данного учебного продукта не установлено | Для сравнения использованы L02 и карточка из курса; полный текст в этом комплекте не воспроизводится; **не выбран** |
| **ISO/IEC 27034-1:2011** | Управление безопасностью приложения в организации, включая отношения сторон | Сложный организационный контекст отсутствует; общая рамка требует значительной конкретизации | Официальная карточка и L03 доступны, полный текст не заявляется изученным; **не выбран** |
| **IEC 62443-4-1:2018** | Жизненный цикл продукта для промышленной автоматизации | Helpdesk не промышленный компонент; отраслевые требования не дают полезного основного каркаса | Официальная карточка и L03 доступны; **не выбран** |

Дополнительный источник — **OWASP ASVS 5.0.0**, только для конкретизации технических требований. Используем 8.1.1–8.1.2 (документирование доступа к операциям, объектам и полям), 8.2.1–8.2.3 (его реализация), 8.3.1 (проверка в доверенном сервисном слое) и 6.3.1 (защита от перебора). Это выборочные требования; соответствие полному уровню ASVS не заявляется. Сам ASVS не заменяет процессную рамку SSDF.

### Адаптация семи задач SSDF

Оригинальные формулировки проверены по [NIST SP 800-218](https://doi.org/10.6028/NIST.SP.800-218). Ниже дано краткое изложение смысла и наше локальное решение. Указанные инструменты и интервалы проверки выбраны для Helpdesk, а не предписаны NIST.

**A01 — PO.1.2: определить и поддерживать требования безопасности к разрабатываемому ПО.** Применимо полностью в границах продукта. Для каждого изменения автор проверяет затронутые R01–R13 и обновляет правила [API](docs/api.md). Результат — конкретное разрешённое/запрещённое поведение и соответствующий тест или план. Проверка: для чтения, записи и переходов состояний можно определить действующее лицо, объект и ожидаемый ответ. Исключены требования к отсутствующим почте, файлам и внешнему входу; при их добавлении профиль пересматривается.

**A02 — PO.2.1: определить роли и обязанности на всём жизненном цикле.** Применимо частично: один студент выполняет разработку, самопроверку и подготовку выпуска. Результат — распределение функций и процедура самостоятельной проверки в разделе 4. Проверка: для каждой контрольной точки назван ответственный и сохраняемый результат. Независимость проверяющего не имитируется; замечания преподавателя фиксируются отдельно, если получены. Подтверждение формата не подменяется выдуманным review партнёра.

**A03 — PO.4.1: определить критерии проверок безопасности и отслеживать их в жизненном цикле.** Применимо полностью. Автор задаёт Q1–Q4, выполняет обязательные проверки и отмечает отклонения. Результат — протокол с версией, исходом и ссылками. Проверка: провал контроля доступа блокирует выпуск; отсутствие запуска не считается успешным тестом. Исключения имеют основание, срок и компенсирующую меру. Корпоративные комитеты и согласование нескольких подразделений не вводятся.

**A04 — PS.1.1: хранить код и конфигурации с минимально необходимыми правами.** Применимо частично до публикации. Автор использует Git, не включает локальные секреты, ограничивает права workflow чтением, закрепляет сторонние actions коммитами. Перед публикацией проверяет историю и права репозитория. Результат — история изменений, конфигурация CI и проверка комплектности. Проверка: секреты исключены, изменения прослеживаются, доступ на запись предоставлен только необходимым субъектам. Настройки GitHub не считаются выполненными, пока репозиторий не опубликован.

**A05 — PW.4.4: проверять сторонние компоненты на соответствие требованиям проекта в течение их жизненного цикла.** Применимо полностью для используемых компонентов. Автор фиксирует зависимости и образы, планирует состав компонентов (SBOM) и анализ известных уязвимостей перед выпуском. Результат — отчёт с датой базы уязвимостей и решениями по находкам. Проверка: отчёт относится к нужной версии, прямые и транзитивные зависимости сопоставлены с поставкой. Разработка собственного сканера и аудит исходного кода всех библиотек исключены. Отчёт планируется на ЭК2; его наличие сейчас не заявляется.

**A06 — PW.8.2: определить область тестирования, провести его и разобрать обнаруженные проблемы.** Применимо полностью. Автор связывает сценарии с рисками, выполняет позитивные, негативные и конкурентные проверки на PostgreSQL, сохраняет результат. Проверка: ошибки доступа воспроизводятся через API, а тесты изменяют ожидание при регрессии. Результат — исходники тестов, XML и интерпретация охвата. Нагрузочная устойчивость и все возможные последовательности запросов не следуют из прохождения небольшой регрессии.

**A07 — RV.2.1: собрать сведения о риске для выбора реакции на уязвимость.** Применимо полностью как правило обработки. При находке автор сохраняет версию, сценарий, влияние, применимость, приоритет и решение. Для исправления повторяет исходный сценарий и соседнюю регрессию. Результат — запись о разборе с проверяемым основанием. Проверка: сырой вывод сканера не приравнен к подтверждённой уязвимости, исключение не скрывает блокирующую проблему. Пока реальных сообщений об уязвимостях нет, не создаются фиктивные инциденты.

Эти семь задач охватывают требования, ответственность, защиту материалов, компоненты, проверки и реакцию. Полное соответствие SSDF не заявляется. При анализе текущего состояния особенно проверяются воспроизводимость, права БД и отсутствие контроля частоты входа. Детальный технологический выбор остаётся предварительным до лекций 06–08.

G01 относится к организационной готовности комплекта; G02–G07 задают дальнейшую работу и ограничения. Нельзя трактовать их все как подтверждённые эксплуатируемые уязвимости.

## 4. Целевой Secure SDLC

Жизненный цикл безопасной разработки (Secure SDLC) для Helpdesk состоит из коротких повторяемых действий. Процесс относится к одному продукту и одному планируемому выпуску; роли обозначают функции одного исполнителя, а не вымышленные должности.

### Практики и ответственность

| Когда | Обязательное действие | Ответственный и результат | Основание |
| --- | --- | --- | --- |
| До изменения | Уточнить затронутый сценарий риска, правила доступа и границы | Автор как владелец продукта; обновлённое правило и критерий приёмки | A01, R01–R13 |
| При реализации | Использовать DTO с разрешёнными полями, параметризованные запросы, транзакции и стандартные механизмы безопасности | Автор как разработчик; код, миграция и тест | A01, A06 |
| После изменения | Просмотреть diff отдельным проходом; проверить чтение, запись, ошибки и побочные пути | Автор как проверяющий; замечания и исправления с коммитами | A02, G07 |
| До включения в основную ветку | Выполнить сборку, регрессию и проверку секретов; проверить соответствие текста фактическому коду | Автор и CI; результат запуска для конкретного состояния | A03, A04, A06 |
| При обновлении зависимостей и перед выпуском | Сопоставить компоненты, SBOM и результаты анализа; разобрать существенные находки | Автор как сопровождающий; отчёт и решения | A05, G02 |
| Перед выпуском | Проверить комплект и остаточный риск, выбрать выпуск / выпуск с условиями / отсрочку | Автор как ответственный за выпуск; решение по конкретному кандидату | A03, R13 |
| После сообщения о проблеме | Проверить применимость, оценить ущерб, исправить и повторить проверку | Автор как сопровождающий; запись триажа и регрессия | A07 |

При изменении аутентификации обязательны проверки сессий и CSRF; при изменении SQL — проверки данных и транзакций; при изменении образа — повторный запуск Compose. Добавление файлов, HTML-интерфейса или внешнего API требует пересмотра рисков до реализации. Нагрузочный анализ, сложный динамический сканер и проверка промышленной инфраструктуры не запускаются формально для каждого небольшого изменения.

### Контрольные точки

**Q1 — пригодность объекта и требований.** Перед началом анализа есть конкретная версия, запуск, правила двух ролей и разрешённые учебные данные. Можно изменить приложение и повторить проверку. Если объект или данные недоступны, работа с таким объектом не принимается; границы уменьшаются.

**Q2 — готовность изменения.** Перед включением изменения проходят сборка и автоматические тесты. Для изменения доступа нужен как минимум разрешённый и запрещённый сценарий. Автор отдельно просматривает diff и убеждается, что исключения Git/Docker не пропускают секреты. Ошибка теста, отсутствие зависимости или пропущенный Docker-тест означает непрохождение точки, а не «нет находок».

**Q3 — готовность кандидата выпуска.** Для `v1.0.0` запланированы регрессия, чистый запуск, миграции, разбор зависимостей и образа, состав компонентов и существенные результаты M1–M7. Неподтверждённое закрытие R01–R04, утечка секрета, неисправная миграция или применимая критическая уязвимость блокируют выпуск. Для ЭК1 требуется только обоснованность этого плана и проверяемое текущее состояние; Q3 ещё не объявляется пройденной.

**Q4 — связь решения с поставкой.** Перед release tag автор сверяет commit, конфигурацию, схемы БД, хэш образа, результаты и условия использования. Выпускается именно проверенный кандидат. При изменении кода или зависимостей после проверки затронутые проверки повторяются. `ek1` — отметка учебной сдачи, а не разрешение на публичную эксплуатацию.

### Исключения, принятие риска и эскалация

Исключение записывается в `project.md` или issue со ссылкой на версию и свидетельство. Обязательны: правило, причина, затронутый риск, компенсирующая мера, ответственный, срок пересмотра и решение. Фраза «не успели» без описания последствий основанием не является.

**E01, действующее ограничение каркаса:** HTTP без TLS допустим только на `127.0.0.1`, с искусственными данными и локальными случайными паролями. Ответственный — автор; пересмотр обязателен перед любой сетевой публикацией и перед решением по `v1.0.0`. Мера снижает риск передачи сессии по сети, но не защищает от администратора компьютера.

**E02, процессное ограничение:** индивидуальный формат не обеспечивает независимый review. Автор использует отдельный проход проверки, тесты с несколькими субъектами и проверку требований по рубрике. Ограничение остаётся в тексте проекта до конца курса. Не заявляется, что самопроверка равнозначна проверке напарника.

Нарушение изоляции чужих обращений, раскрытие внутренних заметок и обход полномочий не принимаются как исключения даже для учебной демонстрации. При споре о допустимости объёма или индивидуального формата вопрос передаётся преподавателю; технический риск автор сначала воспроизводит и описывает, затем выбирает исправление или отсрочку. Преподаватель не назначается исполнителем разработки и не изображается уже согласовавшим выпуск.

### Что реализуется в рамках курса

На ЭК1 имеются каркас, миграции, ограниченная регрессия, Docker-сборка, инструкция и проект процесса. Публикация и первый запуск CI завершают организационную подготовку ЭК1. На ЭК2 планируются апробация выбранных методов, разбор результатов, одно обоснованное улучшение, повторная проверка и решение о выпуске. Резервирование, наблюдение и полноценная эксплуатация могут попасть в последующую дорожную карту, если не станут блокирующими для уточнённого контекста.

## 5. Технологический профиль

Это предварительный план ЭК1. После лекций 06–08 инструменты и глубину можно изменить с объяснением причины. Для уже применённых средств версии зафиксированы в Gradle, lock-файле и образах; для ещё не выбранных версия определяется перед апробацией. Ниже нет выдуманных отчётов о будущих запусках.

### M1. Анализ требований и правил доступа

**Риски:** R01–R04; **этап:** требования и проектирование. Гипотеза: для каждого пути к обращению можно явно определить разрешённого субъекта, операцию и поля. Автор сопоставляет таблицу API, выборочные требования ASVS 5.0.0 и реализацию сервиса, включая очередь и повторное открытие. Результат — карта доступа и список несоответствий со ссылками. Самопроверка идёт в обратном направлении: от каждого обработчика к правилу и тесту. Не покрывает фактическую конфигурацию сервера и все ошибки библиотек. Основная цена — ручной разбор небольшого числа операций, внешний инструмент не нужен.

### M2. Негативные, регрессионные и конкурентные проверки

**Риски:** R01–R04, R06–R07, R09; **этап:** реализация и проверка изменения. Инструменты: JUnit 5 и Spring Test из зафиксированного набора зависимостей, Testcontainers 1.21.4 и тот же PostgreSQL, что в Compose. Гипотеза: замена субъекта или недопустимого состояния не раскрывает и не меняет данные; два одновременных назначения дают один успех. Команда: `./gradlew test --no-daemon`. Результат — код сценария, XML, версия объекта и разбор отказов. Автор повторяет запуск с чистой тестовой БД; конкуренция проверяется барьером старта, а не случайной задержкой. Текущий набор уже подтверждает часть baseline; на ЭК2 расширяется по карте покрытия. Не покрывает все последовательности запросов, длительную нагрузку и сеть. Это основной метод, так как типовой сканер не знает, кому принадлежит обращение.

### M3. Анализ кода, ошибок и секретов

**Риски:** R03, R06, R08, R11; **этап:** реализация и review. Автор просматривает пути от входа к SQL, ответу и журналу, отдельно проверяет историю Git, контекст Docker и конфигурации. Для автоматизации рассматриваются Semgrep с правилами для JVM и Gitleaks; окончательные версии и лицензии фиксируются до запуска. Гипотеза: пользовательские поля не формируют SQL и не становятся полномочиями, исключения не возвращают содержимое запросов. Свидетельства — конфигурация, область анализа, существенные находки с подтверждением или отклонением. Самопроверка: вручную пройти минимум один путь, который автоматический анализ не покрывает. Не доказывает безопасность зависимостей или отсутствие логических ошибок. Если инструмент не понимает Kotlin/Spring-поток, это ограничение сохраняется, а не скрывается числом «0».

### M4. Анализ зависимостей и состава поставки

**Риски:** R10, R13; **этап:** сборка и выпуск. План: сформировать SBOM в формате CycloneDX и проверить JVM-компоненты и контейнер, например Trivy. Точная версия инструмента, дата базы и digest проверяемого образа сохраняются перед апробацией. Гипотеза: состав runtime-поставки известен, применимость существенных находок разобрана. Автор отделяет зависимости сборки и тестов от runtime, но не считает первые автоматически безопасными. Результат — SBOM, отчёт, область и решения по находкам. Самопроверка: сверить прямые компоненты с Gradle и несколькими транзитивными зависимостями. Не покрывает неизвестные уязвимости, эксплуатационный контекст и подмену доверенного источника. Сбой скачивания базы означает неполную проверку, а не чистый результат.

### M5. Динамическая проверка сессий, ошибок и ограничений

**Риски:** R04–R05, R08–R09; **этап:** проверка работающего сервиса. Основной способ — HTTP-клиент с cookie jar и ограниченные сценарии на собственном локальном экземпляре; исходный [smoke.py](scripts/smoke.py) работает на Python 3 без дополнительных библиотек. Планируются истечение сессии, повторное использование cookie после выхода, неправильный CSRF, ошибки форматов, серия неудачных входов и анализ ответа/логов. Любая серия запросов ограничивается по количеству и времени; целевой публичный сервис не используется. Результат — обезличенный протокол с ожидаемыми и фактическими статусами. Возможный ZAP рассматривается только после настройки аутентифицированной области. Отсутствие браузерного интерфейса ограничивает применимость проверок XSS. Полноценная устойчивость к отказу в обслуживании не заявляется.

### M6. Проверка контейнера, БД и миграций

**Риски:** R09, R11–R12; **этап:** настройка среды и выпуск. Инструменты: Docker/Compose, PostgreSQL и Flyway из закреплённой конфигурации. Автор проверяет UID, доступность портов, read-only filesystem, полномочия роли, первый и повторный запуск схемы, сохранение тома. Результат — команды и безопасный вывод без `docker inspect` переменных окружения. Самопроверка: пустой отдельный том и повторный запуск; рабочие данные не удаляются. Гипотеза: инструкция не требует ручного SQL, приложение не получает полномочий суперпользователя. Не покрывает безопасность хоста, администратора Docker и восстановление из копии. Разделение миграционной и runtime-роли — возможное улучшение G04.

### M7. Воспроизводимость комплекта и контроль выпуска

**Риск:** R13, разрыв G01; **этап:** подготовка сдачи и выпуска. Инструменты: Git, Gradle Wrapper, CI и проверка локальных ссылок. Автор повторяет команды из README, сверяет состав файлов и версию результатов. Результат — tag, идентификатор состояния, журнал запуска, контрольные суммы и решение контрольной точки. Самопроверка выполняется из отдельного чистого checkout без рабочего `.env`. Не обещается побитовая идентичность JAR на разных платформах; проверяется повторяемость сборки, поведения и интерпретации. Подготовленный workflow до его запуска является конфигурацией, а не свидетельством успешного CI.

### Порядок апробации и ожидаемое улучшение

Сначала M1 задаёт карту доступа, затем M2 и M5 проверяют поведение, M3 дополняет анализом кода, M4 и M6 — составом и средой, M7 связывает результаты с выпуском. Все методы ведёт автор. Независимый воспроизводящий пока не назначен; команды и синтетические данные рассчитаны на проверку преподавателем или другим читателем.

| Приоритет | Работа | Критерий завершения |
| --- | --- | --- |
| 1 | Подтвердить R01–R04 и устранить расхождения | Для всех операций есть разрешённый и запрещённый сценарий с фактическим результатом |
| 2 | Разобрать зависимости, настройки и права БД | Существенные находки интерпретированы, область анализа известна |
| 3 | Выбрать полезное улучшение | Обоснован выбор между G03, G04 и иной подтверждённой проблемой; сохранено состояние до изменения |
| 4 | Повторить проверку и принять решение | Есть сравнение до/после, соседняя регрессия, остаточный риск и конкретный кандидат |

Пример проверяемой гипотезы улучшения G03: после введения ограниченного по памяти механизма ограничения попыток входа заданная серия получает контролируемый отказ, обычный вход после установленного интервала остаётся доступным, а чужая учётная запись не блокируется бессрочно. Это пока план, не выполненное исправление. Выбор не зависит от необходимости «обязательно найти уязвимость».

Разделы 6–11 будут дополнены для ЭК2 после фактической апробации. Сейчас не заявляются итоговый триаж, завершённое улучшение, окончательное решение о выпуске и метрики эксплуатации.

## 12. Использование генеративного ИИ

Использован OpenAI Codex на базе GPT-6. ИИ помог сравнить темы, подготовить код Kotlin, SQL-миграции, Docker/Gradle-конфигурацию, тесты, сценарий запуска и первоначальный текст проекта. Ему передавались открытые материалы курса, описание учебного продукта и пример сборки приложения автора. Производственные секреты, содержимое рабочих БД и реальные обращения не использовались.

Проверка включала компиляцию, интеграционные тесты на PostgreSQL, Docker-сборку, реальный HTTP-сценарий, сверку выбранных задач SSDF с официальным документом и отдельный проход по рубрике ЭК1. Фактические результаты находятся в `evidence/`; сгенерированный текст сам по себе свидетельством не считается. Автору перед защитой нужно лично повторить запуск и разобрать решения, перечисленные в [индивидуальной странице](individual/author.md). Такая личная проверка не объявляется уже выполненной за него.
